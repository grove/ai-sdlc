# Keep the catalog relevant

Designate a catalog owner and allow project teams to contribute local variations and learning. Keep the stable identifiers as the text is improved. New ideas can be added with new IDs, while expired entries are marked with a replacement and justification. That way, previous experiment references remain understandable.

|  **Local status**  |  **What should be found**  |
| --- | --- |
| Idea | Concrete task, possible benefit, necessary basis, control and proposal for measurement. |
| Selected for trial | Owner, hypothesis, baseline or plan for baseline, delineation and decision date. |
| Under trial | Versioned setup, real runs, deviations, costs and observed outcomes. |
| Documented useful in given context | Basis for decision, type of task, measurable effect, limitations and plan for duration. |
| Requires customization or more data | Which prerequisites are missing, and which next attempt can clarify them. |
| Discouraged or discontinued in given context | Why the measure did not produce the desired net effect, the consequences and any alternatives. |

<a id="section-1"></a>

## Make the experience discoverable

Associate catalog identifier with problem, hypothesis, task, context version, agent run, verification, delivered version, observation window, and learning decision. Store relevant metadata and links to protected sources. A shared catalog does not need raw prompts, source code, personal data or detailed security findings.

<a id="section-2"></a>

## Revise based on actual changes

Reassess entries when the model, tool, supporting data, control requirements or working method change. Mark the impact locally and test affected tasks before widespread continuation. An experience report from one team should show assumptions and uncertainties, so that another team can make its own assessment.
